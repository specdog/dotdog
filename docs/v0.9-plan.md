# Dotdog 0.8.5+ Plan — Three Doors, One Engine

## Product Insight

Users don't start with specs. They start with plans, tickets, or blank files.
Dotdog meets them at their entry point and pulls them toward spec discipline.

Three personas, one engine:

| Persona | Entry | Command |
|---------|-------|---------|
| Architect | Writes .dog by hand | `dotdog init`, `dotdog compile` |
| Ticket-first | Plans in GitHub issues | `dotdog issues --check` |
| New user | Blank canvas, needs guidance | `dotdog init --guided` |

---

## Feature A: `dotdog init --guided`

### User Story
> I'm new to dotdog. I run `dotdog init my-project --guided`. It asks me 5 questions.
> From my answers it generates SPEC.dog, constitution.dog, and data-model.dog with
> inline comments showing me what to fill in next.

### Implementation

**Command signature:**
```
dotdog init <project> [--guided|-g] [--purpose] [--users] [--rules] [--entities]
```

**Interactive flow (5 prompts):**
1. "What does it do? (one sentence)" — default: "A software project"
2. "Who uses it? (comma-separated)" — default: "developer"
3. "Top 3 rules? (comma-separated)" — default: "tests pass before merge"
4. "Core entities? (comma-separated)" — default: "User"
5. "Package name? (for package.json)" — default: <project>

**Generated output:**
```
specs/my-project/
  SPEC.dog           ← Product section filled, User Stories stubbed with <!-- TODO -->
  constitution.dog   ← Core Rules seeded from prompt #3
  data-model.dog     ← Entity stubs from prompt #4, empty properties
```

**Inline comments in generated .dog:**
```markdown
### Entity: User
<!-- TODO: add properties (fields the entity needs) -->

```yaml
entity: User
type: entity
properties:
  name:
    type: string
    required: true
    description: <!-- TODO -->
states: [active, archived]
```
```

**Non-interactive fallback:**
```
dotdog init rover -g --purpose "Robot harness" --users "operator,agent" \
  --rules "safety first, sim-safe, feature-gated" --entities "Harness,CLI,Safety"
```

**Code changes:**
- `src/cli.ts`: add `-g/--guided` flag to existing `init` command
- `src/cli.ts`: add `promptUser()` function using readline
- No new files, no new deps

**Test cases:**
- Interactive mode creates 3 files with correct content
- Non-interactive flag mode matches interactive output
- Inline TODOs present in generated files
- `validate` passes on generated output

## Feature B: `dotdog issues --check`

### User Story
> I plan in GitHub issues. My team ships code against them. I run
> `dotdog issues --check` and it tells me which closed issues lack spec coverage
> and which entities need state updates.

### Implementation

**Command signature:**
```
dotdog issues [--check] [--repo <owner/repo>]
```

**Output:**
```
my-org/rover
  9 entities → 15 issues: 14/15 covered (93%)

  Uncovered:
    #23 Add stream backpressure helpers

  Drift — closed but entity state is "planned":
    #4  → Harness (closed 3 days ago)
    #7  → Adapter (closed 2 days ago)

  Run `dotdog issues --check` to re-check.
```

**Matching algorithm:**
1. Load .dag, extract entity names + descriptions
2. Run `gh issue list --state all` for the repo
3. For each non-epic issue, score against entity names (10pts direct match, 4pts per description keyword hit)
4. Threshold: score >= 3 → matched
5. Unmatched → uncovered list
6. Matched + closed + entity first state is "planned" → drift list

**Code changes:**
- `src/cli.ts`: new `issues` subcommand
- `src/cli.ts`: port `match_entity()` from `scripts/dotdog-issues.py`
- `src/cli.ts`: `getIssues()` wraps `gh issue list` subprocess
- Remove `scripts/dotdog-issues.py` after port

**Test cases:**
- Mock `gh issue list` output
- 100% coverage on a well-maintained project
- Drift detection fires for closed issues with `planned` entities
- Uncovered issues listed correctly
- Non-epic issues excluded from count

## Feature C: `analyze` integration

### User Story
> I already run `dotdog analyze`. When drift exists, it tells me to run
> `dotdog issues --check`. Discovery in context.

**Change:**
After `analyze` output, add:
```
  ℹ 12 closed issues without entity updates.
     Run `dotdog issues --check my-org/rover` to audit.
```
Only shown when `.git/config` has a GitHub remote. Opt-in via `--issues` flag initially.

## Feature D: MCP tools for agents

### User Story
> An AI agent initializes a dotdog project and audits issue coverage without
> running CLI commands. Two new MCP tools expose the same features programmatically.

### New MCP tools

**`initGuided`** — non-interactive project init. Same as `init -g` flag mode.
```
{ name: 'initGuided', description: 'Initialize a dotdog project from parameters',
  inputSchema: { properties: {
    project: { type:'string' },
    purpose: { type:'string' },
    users: { type:'string' },
    rules: { type:'string' },
    entities: { type:'string' }
  }, required: ['project'] } }
```

**`checkIssues`** — coverage audit. Auto-detects GitHub remote, returns JSON.
```
{ name: 'checkIssues', description: 'Validate spec coverage against GitHub issues',
  inputSchema: { properties: {
    repo: { type:'string' },
    project: { type:'string' }
  }, required: ['repo'] } }
```

### Implementation

- `src/serve.ts`: add two tool definitions to `tools/list` handler
- `src/serve.ts`: add two `if (name === ...)` blocks in `tools/call` handler
- Shared logic: extract `projectInit()` and `checkIssues()` from CLI into
  reusable functions callable by both CLI and MCP

### Code changes
- `src/serve.ts` — 2 new tool defs, 2 new handlers (~30 lines)
- `src/cli.ts` — extract shared functions (~10 lines refactor)
- Zero new files, zero new deps

## Feature E: `dotdog doctor`

### User Story
> Something broke. I run `dotdog doctor`. It checks git, gh, node, dotdog version, validates all my spec projects, finds stale .dag files, and checks issue coverage. One command to know what's wrong.

### Output
```
$ dotdog doctor

  Environment
  ✓ git 2.48.1
  ✓ gh 2.65.0 (authenticated as logohere)
  ✓ node 26.3.0
  ✓ dotdog 0.8.4 (latest)

  Specs
  ✓ rover : 3 .dog files, 100% complete
  ✗ telemetry : stale .dag (spec changed, not recompiled)
     Run: cd specs/telemetry && dotdog compile

  4 checks: 3 passed, 1 failed
```

### Checks
1. `git --version` — installed
2. `gh auth status` — installed + authenticated
3. `node --version` — >= 20
4. All spec projects validate at 100%
5. No stale .dag files (mtime of any .dog > .dag)
6. If issues --check enabled: coverage + drift

### Scope
- New `doctor` subcommand
- Reads cwd for projects, scans specs/ and projects/
- Zero side effects, read-only
- ~80 lines in cli.ts
- No new deps (shells out to git, gh, node)

## Ship Order

1. **Feature A** — `init --guided` (smallest, standalone)
2. **Feature B** — `issues --check` (proven by prototype)
3. **Feature C** — analyze integration (connects A + B)
4. **Feature D** — MCP tools: initGuided + checkIssues
5. **Feature E** — `dotdog doctor` (baseline health check)
